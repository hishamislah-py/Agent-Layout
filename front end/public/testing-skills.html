The skills that find & report security vulnerabilities

A two-stage security testing pipeline. The API Security Skill probes live API endpoints for authentication flaws, CORS misconfigurations, JWT issues, and rate-limiting bypasses. The Static Analysis Skill scans source code statically using Semgrep with third-party Trail of Bits rulesets — and merges findings into a verified SARIF report.

Overview

Two skills, one chain of evidence

The pipeline runs in order. The API Security Skill takes a live endpoint URL and a set of OWASP-aligned test cases, drives real HTTP requests using curl, and records every finding — PASS, FAIL, or partial — with exact response evidence. Every confirmed vulnerability is structured as a Jira-ready finding report.

The Static Analysis Skill clones or reads the source codebase, detects languages, selects the matching official and third-party Semgrep rulesets (Trail of Bits, 0xdea, Decurity), and presents a scan plan for explicit approval before running. Findings are merged into a single SARIF file and filtered to security-relevant, medium-high confidence results. Both skills follow the same OWASP Top 10:2025 + ASVS 5.0 classification framework so findings are consistent and Jira-traceable.

Stage 01 · Black-Box Testing — Live Endpoint to Verified Findings

API Security Skill

evidence-first live-verified api-security-testing Snyk / Community

Golden ruleA finding is only a finding when you have the raw HTTP response to prove it — never from assumption.

A senior penetration tester that takes a live API endpoint and a set of OWASP-aligned test cases, executes each attack scenario via real HTTP requests, and produces structured finding reports with exact response evidence, reproduction steps, and Jira-ready severity ratings.

Purpose

Given a base URL and an endpoint or set of endpoints, it executes a systematic black-box security assessment covering OWASP Top 10:2025 categories — authentication, authorization, injection, CORS, rate limiting, JWT, and information disclosure. Triggers on phrases like "test this API for security issues," "run a security audit on this endpoint," or "check for OWASP vulnerabilities."

Inputs
  • Target base URL + endpoint(s)
  • Valid credentials / JWT token
  • OWASP categories to test
  • Environment (staging / prod)
→
Outputs
  • PASS / FAIL per test case
  • Raw HTTP response evidence
  • Structured Jira finding reports
  • Severity & OWASP classification

Key capabilities

/ auth

Authentication & JWT testing

Brute force, account lockout, rate-limit bypass via email case rotation, JWT algorithm confusion (alg:none), PII in payload, token timing oracle.

/ cors

CORS & header analysis

Preflight and credentialed requests from evil.com and null origins, access-control header audit, server version disclosure.

/ inject

Injection testing

SQL injection (classic, boolean, stacked, time-based), NoSQL injection, email normalization bypass, plus-addressing bypass via validation fields.

/ report

Structured finding reporting

Each confirmed finding becomes a Jira-ready report: summary, description, test steps, expected vs actual, severity, OWASP category, CWE, and fix recommendation.

Workflow

Scope & recon

Identifies target endpoints, required authentication, and applicable OWASP categories. Captures server headers, response shape, and token structure before any attack begins.

Token acquisition

Obtains a valid JWT using provided credentials. Decodes payload (base64) to map claims — user_id, email, role, permissions — for later comparison.

Systematic test execution

Runs each test case with real curl commands. Captures status codes, response headers, and body. Marks PASS or FAIL from what the server actually returns — never inferred.

Evidence capture & triage

For every FAIL, captures the exact response proving exploitability. Triages severity: Critical / High / Medium / Low with OWASP category and CWE reference.

Finding report generation

Produces structured reports with: summary, description, steps to reproduce (with exact curl commands), expected result, actual result, fix recommendation, and OWASP / CWE references. Ready to paste into Jira.

Fix verification

On re-test requests, re-runs the exact original test steps against the live endpoint and compares current response to the original finding. Reports FIXED or STILL OPEN with evidence.

Strengths & guardrails

Strengths
  • Evidence-grounded — every finding backed by exact HTTP response output, never assumed.
  • OWASP-classified — each finding mapped to Top 10:2025 category and CWE for Jira/compliance traceability.
  • Fix-verifiable — re-runs original exact steps; PASS only when server response proves it.
  • Dispute-ready — when a developer disputes a finding, re-tests and provides updated evidence to confirm or downgrade.
Guardrails
  • Authorized targets only — staging / test environments, never production without explicit approval.
  • Never exfiltrates real user data or credentials beyond what's needed to prove the finding.
  • Rate-limited test loops include delays to avoid accidental DoS on shared staging environments.
  • Disputed findings are re-tested, not argued — evidence decides, not interpretation.

Stage 02 · Static Analysis — Source Code to SARIF Report

Static Analysis Skill

approval-gated sarif-verified static-analysis:semgrep-scanner Trail of Bits

Golden ruleNo scan runs without explicit user approval of rulesets — and no finding is reported without raw SARIF evidence.

A security engineer that scans source codebases for vulnerabilities using Semgrep with both official and third-party rulesets (Trail of Bits, 0xdea, Decurity). Detects languages automatically, presents a full scan plan for approval, runs parallel scanners, and delivers a merged, filtered SARIF report with structured findings.

Purpose

Given one or more source directories, it detects languages, selects matching rulesets, and presents a detailed scan plan — rulesets, targets, engine, mode — for explicit user approval before any scan executes. Output is a merged results.sarif with per-scan raw files preserved. Triggers on phrases like "scan the codebase for vulnerabilities," "run semgrep on this project," or "use tob-semgrep."

Inputs
  • Source directory path(s)
  • Scan mode (run-all / important-only)
  • User approval of ruleset plan
  • Output directory (auto or specified)
→
Outputs
  • raw/ per-scan .sarif + .json files
  • results/results.sarif (merged)
  • rulesets.txt (approved list)
  • Structured findings report

Key capabilities

/ detect

Language auto-detection

Globs source files to identify languages (TypeScript, TSX, JavaScript, Python, Go, etc.) and selects matching official and third-party rulesets for each.

/ parallel

Parallel scan Tasks

Spawns all scan Tasks in a single message for concurrent execution — one per language/codebase — dramatically reducing wall-clock scan time.

/ filter

Important-only mode

Pre-filters by severity (WARNING/ERROR) and post-filters by metadata: category=security, confidence ∈ {MEDIUM,HIGH}, impact ∈ {MEDIUM,HIGH}. Raw results are always preserved.

/ merge

SARIF merge & report

Merges per-scan SARIF files into a single valid results.sarif, then generates a severity/category breakdown table with file:line references for all confirmed findings.

Workflow

Resolve output directory

Checks for existing static_analysis_semgrep_N directories and auto-increments. Creates raw/ and results/ subdirs before any file is written.

Detect languages & check Pro

Globs source paths for file extensions, tallies counts per language. Checks for Semgrep Pro availability (semgrep --pro --validate) to enable cross-file taint tracking.

Present plan — hard gate —

Shows exact rulesets (official + third-party), targets, engine, and mode. Waits for explicit user approval. Never spawns scanners without a "yes." Logs approved rulesets to rulesets.txt.

Spawn parallel scan Tasks

All scan Tasks are emitted in a single message. Each runs semgrep --metrics=off with approved rulesets and writes raw .sarif and .json to raw/.

Merge & filter, then report

Merges SARIF files; applies post-filter for important-only mode. Reports: finding count by severity, category breakdown, top findings with file:line, and any issues NOT caught by semgrep that were found manually.

Strengths & guardrails

Strengths
  • Third-party rulesets mandatory — Trail of Bits rules catch vulnerabilities absent from the official Semgrep registry.
  • No telemetry — --metrics=off on every command; no data leaves the machine.
  • Parallel execution — all Tasks in one message; wall-clock = slowest single scan, not sum.
  • Honest coverage — explicitly flags what semgrep missed that was found manually; never over-claims.
Guardrails
  • Hard gate at Step 3 — never runs a scan without explicit user approval of the ruleset list.
  • Never uses --config auto — sends telemetry and reduces ruleset control.
  • All commands use absolute paths — no ambiguity when running from parallel Tasks.
  • Raw per-scan outputs always preserved; post-filter never overwrites unfiltered data.

OWASP Security

shared framework used by both skills owasp-security
⬡ Snyk / Community

PrincipleEvery finding maps to an OWASP category and CWE — no unclassified vulnerabilities, no vague severity ratings.

The security classification and knowledge framework. Covers OWASP Top 10:2025, ASVS 5.0, LLM Top 10 (2025), and Agentic AI Security (2026). Used by both agents to consistently categorize, prioritize, and document findings for Jira and compliance purposes.

Coverage areas

/ top10

OWASP Top 10:2025

A01–A10 classification. Used to tag every finding with its category: A01 Broken Access, A02 Cryptographic Failures, A05 Security Misconfiguration, A07 Auth Failures.

/ asvs

ASVS 5.0

Application Security Verification Standard — provides specific, verifiable requirements used to define "Expected Result" in each test case and fix recommendations.

/ cwe

CWE mapping

Common Weakness Enumeration reference for all static analysis findings: CWE-250 (root process), CWE-312 (cleartext storage), CWE-338 (weak RNG), CWE-20 (input validation).

/ severity

Severity & priority rating

Standardised Critical / High / Medium / Low severity with P0–P3 Jira priority mapping. Ensures consistent cross-finding comparison and triage decisions.

How the skills use it
  • API Security Skill — classifies every finding by OWASP category before writing the finding report. Determines severity and priority.
  • Static Analysis Skill — maps semgrep rule IDs to OWASP/CWE references in the final findings report.
Benefits
  • Consistent classification across all findings — no guessing at severity.
  • Compliance-ready output — OWASP + CWE references satisfy audit requirements.
  • Enables cross-session comparison — same framework across all audits.
  • Provides fix-recommendation vocabulary grounded in industry standards.

secrets detection hardcoded credential scan tob-insecure-defaults Trail of Bits
⬡ Trail of Bits

PrincipleDetect fail-open insecure defaults — hardcoded secrets, weak auth, and permissive configurations that ship safely in dev but become vulnerabilities in production.

The Trail of Bits insecure-defaults skill. Scans for hardcoded API keys, credentials, weak configurations, and permissive defaults that developers introduce during prototyping and forget to remove. Complements tob-semgrep with pattern-matching focused on configuration and secret exposure rather than code logic flaws.

Detection patterns

/ keys

Hardcoded API keys

Detects API keys, tokens, and credentials committed to source files — including Vite define blocks, .env files, and configuration constants.

Weak authentication defaults

Identifies mock/demo authentication (hardcoded user arrays, email-only login, no password validation) left active in non-development code paths.

/ config

Permissive configurations

Flags host: "0.0.0.0" in dev servers, overly permissive CORS configs, missing rate limits, and debug endpoints left open in production builds.

/ cert

Certificate & key exposure

Detects TLS private keys, certificates, and PEM files committed to version control or included in Docker build contexts.

How the skills use it
  • Static Analysis Skill — runs alongside tob-semgrep to catch secrets and insecure defaults not covered by logic-focused Semgrep rules.

Benefits

closes the loop IEEE-829 / ISO 29119 rtm-generator
⬡ QA Lifecycle

PrincipleEvery requirement needs a test-case ID — distinguish "tested" from "passed", and never go live with critical requirements untested.

A Senior QA Lead skill that builds a bidirectional Requirements Traceability Matrix — mapping business and functional requirements to test cases, execution results, and defects — for coverage proof and audit sign-off.

What it produces

/ catalog

Requirement & TC catalog

Extracts and IDs requirements (BR / FR / NFR) and test cases from the provided documents.

/ matrix

Bidirectional trace

Forward (requirement → test) and backward (test → requirement) traceability, flagging gaps and orphan tests.

/ dashboard

Coverage dashboard

Covered / partial / not-covered, pass / fail / blocked, defect linkage, and overall coverage, execution, and pass rates.

/ signoff

Gaps & sign-off

Gap-analysis recommendations and a GO / NO-GO / conditional sign-off block for QA, BA, PM, and UAT.

How the agents use it
  • Consumes requirements from the BRD / FRD Analyzer and the specs the QA Automation Agent produces, mapping each to coverage.
  • Mirrors the agents' journal discipline — a verifiable, auditable record of what's tested and what passed.
Benefits
  • Proves coverage — nothing missed, nothing over-tested.
  • Surfaces untested critical requirements before release.
  • Audit- and compliance-ready (e.g. 100% RTM for fintech / healthcare).
  • Scales from inline markdown to a color-coded Excel workbook.

Shared rules

How the two skills work together

Both obey the same evidence standard, the same classification framework, and the same approval discipline — which is what lets findings from one feed directly into reports from the other.

Evidence, never assumption

A finding is only a finding when the raw HTTP response or SARIF output proves it. Plausible-but-unverified issues are flagged as "possible" — never reported as confirmed.

One classification standard

Every finding — whether from black-box API testing or static analysis — is classified by the same OWASP Top 10:2025 category and CWE reference, making the full audit report internally consistent.

Fix verification closes the loop

The API Security Skill re-runs exact original test steps when a fix is claimed. FIXED only when the server response proves it — not when the developer says "implemented."
