The agents that build & maintain the test suite

A two-stage Playwright pipeline. One agent turns a written test case into a verified, runnable spec by driving a real browser. The other restructures those specs into a clean Page Object Model — and re-runs them to prove nothing changed. Both work from the same codified skills.

Overview

Two agents, one chain of custody

The pipeline runs in order. The QA Automation Agent takes a human-written test case, drives the page step-by-step through the Playwright MCP browser, and writes a spec that is a transcript of a real, successful run — never code from imagination. It records every run in a journal.

The POM Refactor Agent reads that journal first, then restructures the working specs into a maintainable Page Object Model — extending page files in place, flagging conflicts for human review, and re-running the suite to confirm behaviour is preserved. Both agents follow the same two codified skills — a locator strategy and a spec-authoring standard — so their output stays consistent and interchangeable.

Playwright QA · Stage 01 · Authoring — Story to Verified Spec

QA Automation Agent

snapshot-firstlive-verifiedplaywright-story-executor

Golden ruleCode is a transcript of a real, successful run — never written from imagination.

A senior QA / SDET engineer that takes a human-written test case or user story and turns it into a verified, runnable Playwright test — by first executing the steps live through the Playwright MCP browser, then writing code only from what actually worked.

Purpose

Given a URL, a sequence of steps, and an expected result, it produces a working @playwright/test spec. It triggers on phrases like "run this test case," "automate these steps," or "turn this user story into a Playwright test."

Inputs
  • Entry URL
  • Ordered manual steps
  • Test data / credentials
  • Expected final outcome
→
Outputs
  • tests/<name>.spec.js
  • PASS / FAIL per step
  • test/qa-agent-memory.md journal

Key capabilities

/ parse

Atomic step breakdown

Splits a test case into ordered steps, separating actions (navigate, type, click) from assertions (expected results).

/ drive

Live browser execution

Drives a real page snapshot-first, verifying each step took effect before moving to the next.

/ generate

Transcript-based code

Writes a parameterized spec mirroring the actual run, with real expect() assertions and step comments.

/ remember

Persistent journal

Logs every run — pass/fail, locators, errors — so history is auditable across sessions.

Tools / skills

File operations: Read, Write, Edit, Glob, Grep.
Playwright MCP browser tools: navigate, click, type, fill-form, press-key, hover, select-option, drag, file-upload, snapshot, screenshot, console-messages, network-requests, evaluate, tabs, wait-for, dialog-handling, resize, install, close.

Codified skills: follows playwright-locator-strategy when choosing every element, and playwright-spec-authoring when turning the completed run into the spec file.

Workflow

Analyze

Reads the full case and breaks it into atomic actions and assertions; identifies the entry URL, inputs, and expected outcome.

Clarify (gate)

Asks all ambiguity / safety questions in one batch before touching the browser. Proceeds silently if nothing is unclear.

Execute live — snapshot-first

For each step: snapshot the page, locate the exact element (per the locator strategy), act, then re-snapshot to confirm. Assertions are marked PASS or FAIL from what is actually present.

Write the test code

Only after a step succeeds does it write that step's code — applying the spec-authoring skill: // Step N comments, parameterized data, real assertions.

Update memory

Appends a terse, factual run entry to test/qa-agent-memory.md — name, date, URL, result, steps executed, failure detail, notes.

Strengths & guardrails

Strengths
  • Reliability — specs reflect verified real behaviour, not guesses.
  • Strict locator policy — role / accessibility first, getByTestId fallback, CSS/XPath only as a flagged last resort.
  • Safety-conscious — confirms destructive actions; never hard-codes secrets.
  • Traceability — the journal shows what's been tested, what passed, and which step/locator last failed.
Guardrails
  • No destructive actions without explicit confirmation.
  • One recovery attempt per failing step, then stop and report — never fabricate a pass.
  • Never commits or echoes real credentials (parameterized via process.env).
  • Prefers browser_wait_for over fixed timeouts.

Playwright QA · Stage 02 · Authoring — Spec to Page Object Model

POM Refactor Agent

behaviour-preservingre-run verifiedpom-refactor-agent

Golden rulePreserve behaviour first, improve structure second — never invent a locator or method.

A senior test-architecture engineer that restructures working Playwright specs into a clean, maintainable Page Object Model without changing what the tests verify. Language-aware across JavaScript, TypeScript, Java, and Python bindings.

Purpose

It reads existing specs, identifies each screen by its URL, and extracts locators and actions into page-object classes under tests/pages/. The original spec is left untouched; the refactored version is written to tests/specs/ and verified by an actual test run. Triggers on "refactor into POM," "convert specs to page objects," or "apply POM pattern."

Inputs
  • Working Playwright spec(s)
  • QA + POM run journals
  • package.json / tsconfig.json
  • Existing pages / fixtures
→
Outputs
  • tests/pages/*.js page objects
  • tests/fixtures/fixtures.js
  • tests/specs/<name>.spec.js
  • test/pom-refactor-memory.md journal

Key capabilities

/ partition

URL-driven screens

Partitions specs into screens by URL, naming each page file from the path — /control/users → UsersPage.js.

/ merge

Safe in-place extend

Extends existing page files, deduping locators and methods; conflicting bodies are flagged for review, never overwritten.

/ auth

storageState extraction

Lifts repeated inline logins into a global-setup storageState fixture so tests start pre-authenticated.

/ teardown

Teardown migration

Moves UI-based cleanup into named page methods (e.g. deleteUser), preserving safety guard variables.

Tools / skills

Read, Write, Edit, Glob, Grep, Bash. The Bash access is what lets it actually run npx playwright test to verify the refactor preserved behaviour before declaring success.

Codified skills: applies playwright-locator-strategy to every locator it lifts onto a page object, and reuses the language-detection rules of playwright-spec-authoring to match the repo's module system (ESM / CJS / TypeScript) when emitting the refactored spec.

Workflow

Read memory (always first)

Checks the QA journal and its own. Will not refactor a spec the QA journal marks FAIL; honours past human decisions on flagged conflicts.

Discover & inspect

Detects the module system (ESM / CommonJS / TypeScript) and conventions, then maps every screen transition, locator, action, and teardown block.

Clarify (gate)

Batches all genuinely ambiguous questions — unclear screen names, teardown intent, test-data handling, method conflicts — before writing code.

Identify screens & build page objects

Partitions by URL using the step-attribution rule (an action belongs to the screen you're on), then creates or extends page objects on a shared BasePage, choosing locators per the locator strategy.

Higher-order refactors

Applies storageState auth and teardown migration where present; leaves test data in place by default unless explicitly asked to move it.

Fixtures, write & verify

Writes fixtures and the refactored spec, then runs npx playwright test. One recovery attempt on failure, else stop and report.

Update memory

Appends a detailed entry to test/pom-refactor-memory.md — paths, module system, verification result, files touched, conflicts flagged.

Strengths & guardrails

Strengths
  • Behaviour-preserving — verified by a real run; "looks right" is never a pass.
  • Non-destructive merging — originals untouched; conflicts flagged via _REVIEW_<hash>.
  • Cross-agent awareness — reads the QA journal so it won't build on a known-broken test.
  • Clean conventions — action-named methods, no duplication, shared logic on BasePage.
Guardrails
  • Never modifies the original spec — output lives only under tests/specs/.
  • Never overwrites a method body — always flags for review.
  • Never invents a missing locator — stops and asks.
  • One verification recovery per run; PASS only if the run exits 0.

Skills

The skills both agents draw on

Reusable, codified standards invoked proactively during a run. They are what keep the two agents' output consistent — so a spec authored by one is structured exactly as the other expects.

skill · 01

Playwright Locator Strategy

sharedused by both agentsplaywright-locator-strategy

PrincipleChoose the most stable locator available, dropping a tier only when the current one is genuinely ambiguous or unavailable.

Decides how every element is targeted — in a strict priority order, with a hard rule that each locator must resolve to exactly one element and must never be invented without confirming it against the live page.

Priority order

Role / accessibility — the default

getByRole, getByLabel, getByPlaceholder, getByText. Used whenever the element exposes a stable role plus an accessible name.

Test ID — the fallback

getByTestId targeting data-testid. Used only when role-based selection is ambiguous or unstable.

CSS / XPath — last resort

Only when nothing better exists, and always with a // TODO: brittle locator — <reason> comment explaining why.

How the agents use it
  • QA agent — picks the locator for every action and assertion during the live run, narrowing (scope, { exact: true }, .filter()) rather than dropping to CSS when a role matches several elements.
  • POM agent — applies the same order when lifting locators onto page objects, and preserves existing brittle-locator TODO comments verbatim.
Benefits
  • Locators survive refactors because they target user-facing attributes, not DOM structure.
  • One element per locator eliminates a common class of flaky tests.
  • Brittle selectors are visible and justified, never silent.
  • Identical rules across agents mean handoffs need no re-checking.
Tier 1
getByRole · getByLabel · getByPlaceholder · getByText
Tier 2
getByTestId (data-testid)
Tier 3
CSS / XPath — flagged with // TODO: brittle locator
Hard rule
Resolve to exactly one element · never invent · prefer user-facing attributes

skill · 02

Playwright Spec Authoring

QA-primarylanguage rules sharedplaywright-spec-authoring

PrincipleWrite the spec only from steps that actually ran — every statement mirrors a real action, every locator one resolved live.

Defines how a completed run becomes a clean @playwright/test file: language detection, file naming and location, body structure, mapping assertions to web-first expect(), and safe handling of data and secrets.

What it standardises

/ language

Match the repo

Detects the module system first — emits TypeScript (.spec.ts) when tsconfig/TS deps are present, else JavaScript, matching existing import style.

/ file

Naming & structure

kebab-case under tests/, one test() block per case, standard import of test and expect.

/ body

Steps & assertions

Mirrors each step in order with a // Step N comment; turns each assertion into a real web-first expect().

/ data

Data & secrets

Parameterises URL and inputs as top-level consts; reads anything secret-like from process.env, never hard-coded.

How the agents use it
  • QA agent — its primary authoring standard: after the live run succeeds, it writes the spec exactly to this structure, referencing the locator strategy for each selector.
  • POM agent — reuses the language-detection rules so the refactored spec it emits matches the repo's module system and extension.
Benefits
  • Specs run as written — no references to helpers or fixtures that don't exist.
  • No fixed sleeps; relies on auto-waiting and web-first assertions for stability.
  • Secrets stay out of the codebase and out of version control.
  • Consistent shape makes every spec predictable to read, review, and later refactor.

Assertions

Shared rules

How the two agents work together

Both obey the same constraints and the same skills, which is what lets the output of one feed safely into the other.

Verify, never assume

Every result is grounded in a real browser run. A spec that wasn't executed, or a refactor that wasn't re-run, is never reported as passing.

One shared locator policy

The locator-strategy skill is identical across both agents: role / accessibility first, getByTestId fallback, CSS/XPath only as a flagged last resort.

A memory trail connects them

The QA agent writes a journal; the POM agent reads it before refactoring — so structure is never built on a known-broken test.
