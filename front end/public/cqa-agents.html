Agent Catalog · 8 agents · 7 dimensions

The agents that assess code quality

A Docker-based pipeline that runs 20+ static-analysis and security tools over any codebase, then applies eight specialist AI agents that synthesise raw tool output into scored, ISO 25010–aligned quality chapters. Every agent runs on the orchestrator's model (model: inherit) and writes one structured block into a canonical assessment.json.

Model  claude-sonnet (inherit) Dimensions  7 · ISO 25010 Frameworks  OWASP Top 10 2025 + API Top 10 2023

Overview

How the agents work

Each agent receives a pre-filtered findings slice (only the findings relevant to its dimension), a samples manifest of up to 50 source files it may read, and a set of optional structured-evidence artefacts (knowledge graph, reverse-engineering files, semantic-search results). Agents use only read-only tools — Read · Grep · Glob · Bash — and write a structured JSON block with a 0–10 dimension score, a prose narrative, top findings, and prioritised recommendations.

Seven dimension agents run in parallel; an eighth — the Critical File Audit agent — runs on demand for god-class candidates and feeds confirmed findings back into the Security and Maintainability agents. Where evidence is missing, an agent writes a structured failure record rather than scoring on absent data, and the report surfaces a Coverage Limitation instead.

Dimension 01 · Security

Security Agent

dimension agentOWASP Top 10 2025API Top 10 2023CWE

Golden ruleScore on confirmed exploitability, not scanner noise — quote the evidence and map every finding to OWASP and CWE.

Produces the Security chapter. It reads the full method body behind every critical/high finding, confirms whether it is actually exploitable, and maps the surviving findings to OWASP categories and the API Top 10.

Evidence inputs
  • findings slice (dimension = security)
  • samples manifest (≤ 50 files)
  • user-journeys.json · db-analysis.json
  • design-recovery.json · socraticode-impact.json
→
Outputs
  • Dimension score (0–10)
  • OWASP + CWE mapping
  • OWASP API Top 10 coverage
  • Confirmed findings + recommendations

Core analysis steps

/ confirm

Exploitability triage

Reads the full method for each critical/high finding and tags it confirmed, requires-validation, or false-positive — quoting evidence verbatim.

/ map

OWASP + CWE

Maps every finding to OWASP Top 10 2025 and CWE; for API-heavy repos, to OWASP API Top 10 2023.

/ api

API Top 10 coverage

Per category: confirmed-clean, has-findings, or requires-DAST — covering BOLA, broken auth, mass assignment, resource consumption and function-level authz.

/ cve

CVE reachability

Verifies whether a vulnerable library is actually called vs. imported-only vs. transitive; downgrades unused-library CVEs even if flagged critical.

Scoring anchors

ScoreCondition
9–10Zero criticals, zero highs, defence-in-depth visible across auth/authz layers.
7–8Zero criticals, ≤ 3 highs with clear remediations, structured security-event logging.
5–61–2 patchable criticals, ≤ 8 highs, no systemic access-control failure.
3–4≥ 3 criticals or systemic auth/authorization issues across surfaces.
0–2Exploitable secrets in git history, broken access control in production paths, confirmed injection.

Dimension 02 · Maintainability

Maintainability Agent

dimension agentISO 25010Cyclomatic ComplexityMutation Index

Golden ruleSeparate inherent complexity (the domain is hard) from accidental complexity (poor design) — and put a number on onboarding time.

Assesses complexity, duplication, accumulated debt and coupling, and estimates how long a new engineer needs to become productive in the codebase.

Evidence inputs
  • findings slice (complexity, duplication, debt, naming)
  • db-analysis.json (god tables)
  • design-recovery.json (layer map)
  • knowledge-graph.json · socraticode-impact.json
→
Outputs
  • Dimension score (0–10)
  • Onboarding-time estimate (weeks)
  • Coupling hotspots + cycle break strategies
  • ISO 25010 subcharacteristic narrative

Required narrative elements

/ complexity

Inherent vs accidental

Distinguishes domain-driven complexity from complexity introduced by poor design choices.

/ onboarding

Onboarding estimate

Explicit estimate in weeks with justification: 1–2 (clean, ≤ 50k LOC) through 6+ (spaghetti, high churn).

/ iso

ISO 25010 subcharacteristics

Cites modularity, reusability, analysability, modifiability and testability.

/ cycles

Cycle break strategies

Names a break strategy for each detected circular dependency.

Scoring anchors

ScoreCondition
9–10Avg CC < 10, duplication < 3%, Maintainability Index > 80, clean modules.
7–8Avg CC < 15, duplication < 8%, MI > 65, some coupling hotspots.
5–6Avg CC < 20, duplication < 15%, growing technical-debt backlog.
3–4Several god classes, high duplication, hard to test independently.
0–2Spaghetti architecture, no module boundaries, duplication > 40%.

Dimension 03 · Architecture

Architecture Agent

dimension agentFitness ViolationsC4 / MermaidDependency-Cruiser · Deptrac

Golden ruleJudge the structure against its own intended layering — and name a concrete break strategy for every cycle.

Evaluates layering fitness, circular dependencies, extensibility and structural coupling, and renders a verdict from clean through spaghetti.

Evidence inputs
  • findings slice (fitness, dependency, circular)
  • design-recovery.json (C4, layer map)
  • user-journeys.json · design-nfr-candidates.md
  • frontend-business-logic.json · knowledge-graph.json
→
Outputs
  • Dimension score (0–10)
  • Layering verdict
  • Cycle resolution + extensibility assessment
  • NFR fitness · business-logic leakage

Required analysis sections

/ verdict

Layering verdict

clean · mostly-clean · inconsistent · spaghetti — based on violation patterns and layer contracts.

/ cycles

Circular dependency resolution

Per cycle: mediator service, event bus, or interface-extraction strategy.

/ extend

Extensibility

Plugin points, multi-tenancy readiness and domain isolation.

/ leak

Business-logic leakage

For JS/TS repos: client-side logic that should be server-only, with its security and maintainability implications.

Scoring anchors

7–8Mostly clean, ≤ 5 violations, no circular dependencies.
5–6Inconsistent layering, some cycles, limited extensibility.

Dimension 04 · Operational Readiness

Operational Readiness Agent

dimension agentObservabilitySecrets ManagementMigration Safety

Golden ruleAsk whether this could be run, observed and rolled back in production — and list what must be true first.

Covers error handling, logging, secrets infrastructure, resilience patterns and deployment safety, and ends with explicit production-cutover prerequisites.

Coverage areas
  • Error handling · structured logging
  • Config & secrets infrastructure
  • Monitoring · Dockerfile hygiene
  • Resilience (timeouts, retries, breakers)
  • LLM cost/safety guards · deploy safety
→
Outputs
  • Dimension score (0–10)
  • Schema & migration integrity subsection
  • Production cutover prerequisites
  • Resilience & observability findings

What it produces

/ observe

Observability

JSON-structured logs with correlation IDs, distributed tracing, health endpoints and alerting hooks vs. ad-hoc string logging.

/ secrets

Secrets & config

Secrets manager vs. plaintext env vars vs. hardcoded strings; config-cache correctness.

/ migrate

Schema & migration integrity

When db-analysis.json is present, compares live schema against tracked migrations; untracked live tables = DR risk.

/ cutover

Cutover prerequisites

An explicit list of what must hold before the codebase is production-ready, derived from all dimension findings.

Scoring anchors

ScoreCondition
9–10Structured logs, correlation IDs, secrets in vault, tracing, timeouts on all outbound calls.
7–8Structured logging, basic monitoring, secrets in env (not hardcoded), graceful shutdown.
5–6Mixed logging, some missing timeouts, config inconsistencies, no tracing.
3–4Ad-hoc error handling, secrets in config/code, no retry/breaker patterns.
0–2Console debug logging, secrets in git, no health endpoints, no rollback procedure.

Dimension 05 · Performance

Performance Agent

dimension agentN+1 DetectionCachingQuery Optimisation

Golden ruleFind the query patterns that don't scale — and give a concrete, ORM-appropriate fix for each hotspot.

Hunts N+1 queries, eager-loading gaps, missing caching, wide API payloads and chatty service patterns, with a relative before/after estimate per fix.

Evidence inputs
  • findings slice (N+1, payload, index, slow-query hints)
  • knowledge-graph.json (call-chain depth, hot paths)
  • socraticode-impact.json (query & caching patterns)
→
Outputs
  • Dimension score (0–10)
  • Per-hotspot: file, method, loop, fix
  • Relative capacity estimate per fix

Detected anti-patterns

/ nplus1

N+1 & query-in-loop

DB calls inside iteration over a collection; eager-loading gaps fetched as subsequent queries.

/ payload

Wide payloads

Responses returning all columns when only a subset is needed.

/ chatty

Chatty services

A single handler making more than five outbound service calls.

/ unbounded

Unbounded & nested

Fetch-all on growing tables; loop-in-loop DB access at O(n²) or worse.

Scoring anchors

ScoreCondition
9–10Zero N+1, caching on hot paths, indexed queries throughout.
7–8≤ 2 N+1 on low-traffic paths, caching on critical reads.
5–63–6 N+1 patterns, missing FK indexes, no caching layer.
3–4Pervasive N+1 on main paths, SELECT * on large tables.
0–2Full table scans per request, no indexing, unbounded queries in the request path.

Dimension 06 · Test Coverage

Test Coverage Agent

dimension agentMutation Score (MSI)Assertion QualityBranch Coverage

Golden ruleCoverage that executes code without verifying it is worthless — weight mutation score above line coverage.

Reads coverage and mutation metrics, judges assertion quality, detects brittle tests, and breaks coverage down by business-critical component.

Evidence inputs
  • findings slice (coverage, mutation, organisation)
  • test-coverage-deep.json · test-cases.json
  • user-journeys.json (untested endpoints)
  • knowledge-graph.json (centrality × gaps)
→
Outputs
  • Dimension score (0–10)
  • Coverage-by-component table
  • Brittle-test & flaky-signal findings
  • Priority test targets

Assertion quality signals

/ mocks

Mock saturation

Every dependency mocked = the test verifies very little; flagged as brittle.

/ behaviour

Behaviour vs implementation

Tests asserting private internals break on refactors.

/ flaky

Flaky & slow signals

Sleep calls, retry loops, and suites over five minutes that block CI feedback.

/ msi

Mutation over coverage

90% line / 40% MSI is a worse signal than 70% line / 70% MSI.

Scoring anchors

ScoreCondition
9–1085%+ coverage, critical paths 90%+, MSI ≥ 75%, assertion-dense, < 5 min suite.
7–880%+ coverage, critical paths 85%+, MSI ≥ 60%, some brittle tests.
5–670–80% coverage, critical paths 70–85%, MSI 40–60%, slow but green.
3–450–70% coverage, critical paths < 70%, heavy mock saturation, MSI < 40%.
0–2< 50% coverage, no tests on critical paths, smoke-only tests.

Dimension 07 · Dependency Security

Dependency Security Agent

dimension agentGrype · Trivy · Snyknpm / pip / composer auditgovulncheck

Golden ruleA CVE in an unused library is not a production risk — bucket by reachability, recommend per library not per CVE.

Deduplicates CVEs across many scanners, buckets them by exploitability, and checks licenses and unmaintained dependencies.

Evidence inputs
  • findings slice (multi-tool CVE reports)
  • dependency manifests + lockfiles
  • call-site evidence for reachability
→
Outputs
  • Dimension score (0–10)
  • Deduplicated CVE list by exploitability bucket
  • License & unmaintained-library flags
  • One recommendation per library

How it reasons

/ dedup

Multi-tool dedup

Merges on CVE id + package; uses the most conservative severity; records tool disagreement as uncertainty.

/ buckets

Exploitability buckets

confirmed-exploitable · imported-not-called · transitively-only — unused-library CVEs are downgraded.

/ license

License compliance

Flags GPL/AGPL/SSPL dependencies in distributed products.

/ stale

Unmaintained libraries

2+ major versions behind, no commits in 24+ months, or explicitly deprecated.

Scoring anchors

ScoreCondition
9–10Zero critical/high CVEs, all deps ≤ 1 major version behind.
7–8Zero critical CVEs, ≤ 3 high (all patchable), no unmaintained deps.
5–61–2 critical CVEs (not yet exploitable or unused path), ≤ 10 highs.
3–4Multiple critical CVEs in actively-called libraries, unmaintained core deps.
0–2Known-exploited CVEs (CISA KEV) in production call paths, license violations.

On-demand · Deep audit

Critical File Audit Agent

on-demandFull-file read · no capKnowledge-graph prioritised

Golden ruleRead the whole file like a senior reviewer — highest blast-radius methods first — and confirm before you escalate.

Triggered for god-class candidates (high LOC, finding density or coupling). Unlike the dimension agents, it reads the entire target file with no sample cap, catching issues static scanners miss. Its cfa_ findings feed the Security and Maintainability agents.

Inputs
  • Target file (full, no cap)
  • knowledge-graph node (in-degree per method)
  • semantic search over risk concentrations
→
Outputs
  • cfa_NNN findings (method, line range, severity)
  • Verbatim evidence (≤ 15 lines) + remediation
  • Exploitability evidence + false-positive risk
  • Severity/status summary + verdict

Three phases

/ navigate

Phase 1 — Navigation

Sorts methods by in-degree (callers) and runs targeted semantic searches to build a read-priority list before reading.

/ read

Phase 2 — Guided full read

Reads the file in ≤ 500-line chunks, highest-priority methods first, recording findings as encountered.

/ verify

Phase 3 — Verification

For each requires-verification finding, runs a semantic search to confirm or downgrade.

/ checklist

Audit categories

Authorization, PII & logging, performance, framework anti-patterns and correctness.

Trigger
God-class candidates — high LOC, finding density, or coupling
Feeds
Security Agent · Maintainability Agent (as confirmed findings)
Output prefix
cfa_NNN findings in the canonical schema

Operating principles

The rules every agent works by

One model, inherited

Every agent runs on the orchestrator's Claude model (model: inherit) — consistent reasoning, no extra keys, no version mismatch.

Prose narrative only

The narrative field is flowing prose — no bullets, no headers. Evidence and locations live in the findings array so the report builder owns formatting.

Never score on absent evidence

If a dimension can't be assessed the agent writes a structured failure with populated data_gaps; the report shows a Coverage Limitation instead of a blank.

Prioritised recommendations

Recommendations are ordered critical→low then by lowest effort; every critical finding yields at least one, with explicit depends_on sequencing.
